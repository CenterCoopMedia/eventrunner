## 3. Design

### Data model

No new collection, no new field, no queue, no scheduled job. `send.cjs` stays the only writer. The two endpoints below are the only readers, through the Admin SDK.

`firestore.indexes.json` gains three composite indexes on `sent_emails`: (source ASC, sentAt DESC), (status ASC, sentAt DESC), (source ASC, status ASC, sentAt DESC).

### Endpoints

A new module, `functions/src/email/log.cjs`, exports `createListSentEmailsHandler`, `createGetSentEmailHandler` and lazy `handlers`. `functions/index.js` re-exports them, and `.github/smoke-endpoints.json` gains `listSentEmails` and `getSentEmail`. Both follow `systemErrorsAdmin.cjs`: POST only (405 otherwise), `applyCors`, the gate first, errors through `core/errors.cjs`, the query and the read inside `try` with `internal` on failure.

One id rule, `isValidDocId`, serves `id` and `cursor.id`: a string of 1 to 128 characters, no `/`, not `.` or `..`, and not `__…__`. A bad id is a 400, never a thrown `startAfter` or `doc()`.

`listSentEmails`, POST, tier staff: `requireAdmin({ auth, getConfig }, req, { tier: 'staff' })`.
- Request: `{ q?, source?, status?, limit?, cursor? }`.
- Validation, 400 naming the field: `q` is a string of at most 200 characters after trim; `source` matches `/^[a-z0-9-]{1,64}$/`; `status` is `sent` or `failed`; `limit` is an integer from 1 to 50, default 25; `cursor` is `{ sentAt: finite number, id: isValidDocId }`.
- Query: `where('source', '==')` and `where('status', '==')` when given, then `orderBy('sentAt', 'desc').orderBy('__name__', 'desc')`, `startAfter(new Date(cursor.sentAt), cursor.id)`, and `.select(...LIST_FIELDS)`. `LIST_FIELDS` never holds `html` or `text`, so bodies never leave Firestore on a list.
- Without `q`: `limit(limit + 1)`, as `listSystemErrors` does.
- With `q`: one query of at most `SCAN_CAP = 500` rows. Keep a row when `to` or `subject`, lower cased, contains `q` lower cased; a null field never matches. Stop at `limit` matches. `nextCursor` is the position of the last row examined. It is null only when the query returned fewer rows than it asked for and all were examined.
- Response: `{ rows, nextCursor, scanned }`. A row is `id, sentAt, to, from, subject, templateId, source, status, deliveryStatus, deliveryUpdatedAt, bounceReason, error, retries, bodyStored, bodyTruncated`, with `sentAt` and `deliveryUpdatedAt` in milliseconds through `toMillis`. `toRow` copies named fields only.
- `admin_logs`: none. A list is a read, and `listSystemErrors` writes none.

`getSentEmail`, POST, tier staff.
- Request `{ id }`, checked by `isValidDocId`.
- Response `{ row }`: the list fields plus `html`, `text`, `providerMessageId`, `providerStatus`. 404 `not-found` when the row does not exist.
- `admin_logs`: one row per call through `logAdminAction`, action `view-sent-email`, `docPath` `sent_emails/<id>`. The row names the actor and the path only, never an address or a subject.

Limits: a list reads at most 500 rows with `q` and 51 without; a get reads one. No rate limit: both are admin reads, like `listSystemErrors`, and neither writes except the audit row.

No change. `firestore.rules:448` stays byte for byte. The emulator test in §5 is the proof that the collection stays closed; a unit pin on the line is a drift alarm only.

## 4. Security and privacy

- PII that leaves the deployment: nothing new. Addresses, subjects and bodies go only to an admin browser of this deployment. The searched address stays out of the URL, so client error telemetry and the operator sink never carry it. The preview fetches nothing, so no image host learns that a mail was opened.
- Code and invitation bodies are never stored (`send.cjs:82–92`), so neither endpoint can return one.
- The rules enforce that no client, admin included, reads or writes `sent_emails` (`firestore.rules:448`).
- Signed out: both endpoints return 401, and the route goes to /signin (`AdminApp.jsx:70–81`).
- Signed in, not an admin: both endpoints return 403, the gate shows its denial (`AdminApp.jsx:83–94`), and a direct Firestore read fails.
- Staff admin: can list, search, filter and preview every row, operator alerts included. Cannot edit or delete a row: no write path exists. An operator has the same access.
- Abuse cases and their barriers:
  - Script in a stored body: the empty sandbox and `default-src 'none'`.
  - Tracking pixel, remote font, CSS `url()` or `@import`: `img-src data:` and `default-src 'none'`. Resource hints: `link` elements are removed.
  - Refresh or base tricks: stored `meta[http-equiv]` and `base` are removed; the sandbox also refuses a meta refresh in Chromium.
  - Form or link in a body: the sandbox blocks forms, popups and top navigation; `form-action 'none'`; every link targets `_blank`, which the sandbox refuses.
  - A body reaching the admin's token: the frame has an opaque origin and cannot read the parent's storage.
  - Markup in a subject, address or bounce reason: rendered as React text, never as HTML.
  - Filter injection: `source`, `status` and ids are validated; `q` is only compared in memory.
  - Cost: one list request reads at most 500 rows.
- Residual risk: a click on an SVG link can still navigate the frame itself. The frame stays sandboxed with no script. Bodies come only from server templates and operator overrides.

## 9. Decisions and open questions

Decisions the builder may not change without the director:
1. Search is a bounded scan: 500 rows per request, substring match in memory, no new field, no backfill. Reason: Firestore has no substring query, and `to` is stored as given outside OTP, so an equality lookup misses rows.
2. The status filter is the stored `status` (`sent`, `failed`) only. Delivery state is a word on the row, not a filter. Reason: one field and three indexes. A delivery filter adds two more indexes and a second meaning for "status".
3. Two endpoints: a list without bodies and a get with bodies. Reason: two 100 KB bodies per row make a 25-row page up to 5 MB.
4. `getSentEmail` writes an `admin_logs` row and `listSentEmails` writes none. Reason: reading a person's mail is the sensitive act; `listSystemErrors` sets the precedent for lists.
5. Both endpoints and the page are staff tier. Reason: parity plan lines 87 and 196.
6. The preview is an empty sandbox, a meta content policy, a DOMParser pass that strips `meta[http-equiv]`, `base` and `link`, and a forced `_blank` target, with no remote images. Reason: two independent barriers, and no fetch means no tracking.
7. No feature flag. Reason: the Risks section asks for one only on stranger-text surfaces.
8. No shared admin table or figure sentence component in b2. Both live in the page. Reason: b1 builds ruled tables and figure sentences at the same time, and two new shared components would collide. Wave 6 extraction needs one owner.
9. `firestore.rules` does not change. The emulator test proves the collection is closed; a unit test pins the line.
10. Deviations from the design record, for the director to accept: no sort control, though §8 lists #183 under the sort control (the server order is newest first, and a client sort of one page would mislead); no bulk-action row (§3.4), since the log has no action to apply; `q` is kept out of the URL, though §3.3 keeps a query there (an address in the URL reaches client error reports, see §2).
