## 3. Design

### Data model

`change_requests/{id}`. Written only by the functions below. Read by an admin of either tier through the rules.

| Field | Type | Source |
|---|---|---|
| `message` | string, 1–2000 chars after trim | request body |
| `page` | string up to 200 chars after trim, or null | request body; absent, null, or blank is null; plain text, never a link |
| `status` | `new`, `in_progress`, `done`, `declined` | `new` on create |
| `uid`, `email` | strings | the verified ID token, email lowercased; never the body |
| `createdAt` | timestamp | server clock |
| `updatedAt`, `updatedBy` | timestamp, admin email; null on create | status change |

The id is the client's `submissionKey`. With no key, it is a random UUID. A malformed key is refused (step 3). `change_request_rate_limits/{uid}` holds `{ requests: number[], updatedAt }`. It is server only. No IP hash and no user agent are stored.

### Endpoints

New module `functions/src/admin/changeRequests.cjs`, re-exported in `functions/index.js`, named in `.github/smoke-endpoints.json`. Each is `onRequest({ region })` wrapped in `applyCors`, POST only (else 405). No secrets: nothing sends mail.

**Audit, one rule for all three.** Each write and its `admin_logs` row commit in one `db.runTransaction`. A local `auditRow({ action, docPath, actor, at })` returns exactly the five fields `logAdminAction` writes, into `db.collection('admin_logs').doc()`. The row never holds the message. `store.cjs` is not edited.

**`submitChangeRequest`.** Tier: none. Any signed-in account with a verified email. Order:
1. `features.changeRequests !== true` → 404 `not-found`, "Change requests are not enabled for this event." Nothing is written.
2. `verifyAuthToken` null → 401. No email or `email_verified !== true` → 403.
3. Body over 8 KiB → 413. `message` missing, blank, or over 2000 → 400 `message: …`. `page` present, not null, and not a string, or over 200 → 400 `page: …`. `submissionKey` present and not `^[A-Za-z0-9_-]{8,128}$` → 400. Unknown fields are ignored.
4. `takeChangeRequestRateLimitSlot({ db, uid, now })`: the same transactional window as `takeFeedbackRateLimitSlot`, 5 per 15 minutes per uid, on its own collection. Limited → 429 `rate-limited`, `Retry-After`, `retryAfterSeconds`.
5. Transaction: `tx.get(ref)`. The doc exists → a retry of a stored request: write nothing. Else `tx.create(ref, { … status: 'new' })` and `tx.set(auditRef, auditRow({ action: 'submitChangeRequest', docPath: 'change_requests/<id>', actor: { uid, email } }))`. A failed commit → 500 "Your request could not be saved. Try again." and nothing is stored.
6. 201 `{ id, ok: true }`, the same for a first write and a retry.

**`updateChangeRequestStatus`.** Tier: staff, `requireAdmin({ auth, getConfig }, req, { tier: 'staff' })`. Body `{ id, status }`. Bad id (`isValidDocId`) or status outside the four → 400. Transaction: missing doc → 404; else `tx.update(ref, { status, updatedAt, updatedBy: gate.email })` and the row `updateChangeRequestStatus`. 200 `{ id, status }`. Not flag gated.

**`deleteChangeRequest`.** Tier: staff, as above. Body `{ id }`. Bad id → 400. Transaction: missing doc → 404; else `tx.delete(ref)` and the row `deleteChangeRequest`. 200 `{ id, deleted: true }`. Not flag gated, so staff can clear requests after the flag goes off.

A refused request (4xx) writes nothing and no audit row. If a4 keeps a list or a test of endpoint tiers, add the three names there.

## 4. Security and privacy

- **PII that leaves the deployment:** none. No email is sent and no notifier fires. The requester's uid and email stay in `change_requests` and `admin_logs`, both admin read only. The message is the requester's own text.
- **Rules enforce:** only an admin reads either collection; no client writes either, admin included; the rate-limit store is closed to all.
- **A non-admin can** send a request while the flag is on, signed in with a verified email, 5 per 15 minutes. **Cannot** read any request, their own included, change a status, or remove one.
- **A staff admin can** read every request, change status, remove, and send from the admin form. **Cannot** turn the flag on or off (Features is operator tier).
- **Report path:** only admins ever read a request, so no third party meets the text. The admin page is the report and removal path.
- **Audit trail:** a request never exists without its `submitChangeRequest` row, and a status change or a removal never commits without its row, because each commits in one transaction.
- **Account delete:** `change_requests` rows and `change_request_rate_limits/{uid}` are per-account stores. b3's `deleteAttendee` must remove them (§8, open question 1). The audit rows stay, as b3 keeps `admin_logs`.
- **Abuse cases:** a flood is capped per uid. The emailed-code sign-in caps new addresses (`auth_rate_limits`, the hourly send ceiling). Google sign-in has no server cap, so each Google account gets its own 5 per 15 minutes; the flag is off by default and staff remove entries. Script in a message renders as text: no HTML, no link, and `page` is never an href. A forged sender is impossible, because identity comes from the token. A direct POST with the flag off gets 404. A replayed `submissionKey` finds the doc and writes nothing. Removal leaves no copy of the text, because the audit row holds only the path and the actor.

## 9. Decisions and open questions

Decisions the builder may not change without the director:
1. **One store, one submit endpoint for both entry points; admins read through a listener.** Why: the feedback precedent, and rules stay the enforcement.
2. **Signed-in, verified-email callers only.** Why: gap line 45, "no free text stored against a signed out identity".
3. **Rate limit per uid, 5 per 15 minutes, own collection; no honeypot or time gate.** Why: the uid is the identity, and the numbers match `submitFeedback`.
4. **No mail and no notifier.** Why: no PII leaves, and no send path needs a queue.
5. **The flag gates submission only.** Why: an admin must still remove requests after the flag goes off.
6. **Tiers: submit none, status and delete staff, page staff.** Why: staff runs content; the endpoints and the docket item must state `staff`, because an unstated tier means operator.
7. **Hard delete. Each write commits with its audit row in one transaction, with `logAdminAction`'s fields and no text.** Why: the done line says every submission and every status change writes a row, and the removal copy promises the log keeps the sender. A row written after the write can be lost to a crash or a swallowed failure, and the idempotent retry would never write it. b3 commits its delete audit row the same way. `store.cjs` stays unedited; the shape test catches drift.
8. **Footer dialog, not a new public route.** Why: a route would need a reserved segment in `packages/shared/src/routing.cjs`.
9. **The product copy says "change requests", never "queue".** Why: CONTRIBUTING reserves "queue" for `ticket_sync_queue`. This store is a human inbox with no drain, retry, or schedule.
10. **A row carries the next step, "Decline", and "Remove".** Why: §3.4 names one action per queue row, but the issue needs status changes and an outright removal. The next step keeps the one-action place; the other two are quieter.

Open questions, with the recommended default:
1. Remove an account's change requests and its rate-limit doc when b3 deletes the account? Default: yes, in b3's delete transaction. A request is free text; it must not outlive the identity it was stored against.
2. Limit the public form to approved attendees (`requireAttendeeAccess`)? Default: no. It would refuse a staff admin who is not an attendee.
3. Let a requester see their own requests? Default: no.
4. Show "Sign in to request a change" to signed-out readers? Default: no.
5. Search and sort on the admin list? Default: no; newest first, status filter only.
6. Expire old requests, or add a per-deployment ceiling across all accounts? Default: no; staff remove them, and the flag is off by default.
