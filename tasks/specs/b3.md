## 3. Design

### Data model

- One new field on `users/{uid}`: `pastAttendance`, a list of edition labels such as a year. Organizer-owned. The only writer is `updateAttendee`. Admins read it through the existing `users` read rule. The owner can read it on their own account document. It is not in `PUBLIC_PROFILE_FIELDS`, so it never reaches `users_public`.
- `ORGANIZER_OWNED_FIELDS = ['pastAttendance']` lives in the new `functions/src/users/records.cjs`. Nothing changes in `packages/shared`.
- `admin_logs` rows gain optional detail fields on the export and delete rows only (below). No new collection.

### Endpoints

All three are `onRequest`, POST, JSON, `withCors` as in `approval.cjs`. Each calls `requireAdmin(deps, req, { tier: 'staff' })`, stated explicitly. `uid` values are checked with `internals.readUid` imported from `approval.cjs`, which is not edited.

**`exportAttendees`** (#184), `functions/src/users/export.cjs`. Tier: staff.
- Request: `{ uids: string[], filter: { status, searched } }`. `uids` are the rows on screen, in screen order. `searched` is true when the search field is not blank. The search text is never sent: it can hold a person's name or address, and the audit row outlives a delete.
- Validation: `uids` has 1 to 10,000 entries, each valid under `readUid`. Above the cap the 400 says "uids: at most 10,000 attendees per export. Narrow the filter." Duplicates are dropped and order is kept. `status` is one of the page's five filter values. `searched` is a boolean. Any other body key is a 400.
- Work: `db.getAll` in chunks of 500. An absent account is skipped. Badges and custom badges come from `buildPublicProfile(user, config.badges, config.features)`. Badge ids become their configured labels.
- Columns, in this order: Name (`displayName`), Email, Organization, Role (`jobTitle`), Registration status (stored value), Badges, Past attendance, Social handles (`label: handle`, sorted by label), Profile visibility (stored value). List values are joined with `; `.
- CSV: UTF-8 with a byte-order mark, CRLF line ends, every cell quoted, inner quotes doubled. `escapeCell` adds a leading `'` to a cell that starts with `=`, `+`, `-`, `@`, a tab, or a carriage return. It runs on the joined cell, so a list cell is checked once.
- Response 200: `{ filename: 'attendees-YYYY-MM-DD.csv' (UTC date), csv, rowCount, skipped }` with `Cache-Control: no-store`. The file is never written to Firestore or Storage.
- Audit: one `admin_logs` row `{ action: 'exportAttendees', docPath: 'users', uid, email, at, rowCount, filter: { status, searched } }`, written with `db.collection('admin_logs').doc().set()`, not `logAdminAction` (that helper swallows a failure and has a fixed shape). It is awaited before the response. If it fails, the handler returns 500 with no file. This is a deliberate exception to the store.cjs contract: the export is an egress, not a mutation. Function logs carry counts only, never cell values.

**`updateAttendee`** (#185), `functions/src/users/records.cjs`. Tier: staff.
- Request: `{ uid, pastAttendance: string[] }`.
- Validation: at most 20 entries. Each entry is trimmed, 1 to 40 characters, with no control characters. No duplicates, compared without case. Any other key is a 400 that names the key. Messages use the `field: reason` form that `fieldErrorsOf` splits.
- Work: a transaction reads the account (404 if absent) and merges `{ pastAttendance, updatedAt }`. An empty list is stored as `[]`.
- Response 200: `{ ok: true, uid, pastAttendance }`.
- Audit: `logAdminAction` with `action: 'updateAttendee'`, `docPath: 'users/{uid}'`. Best effort, the same contract as `approveUser`.

**`deleteAttendee`** (#185), same module. Tier: staff. Two phases, both inline in the request. No queue, no scheduled retry.
- Request: `{ uid }`. Before phase 1: 409 when `uid` is the caller's. Read `auth.getUser(uid)` (not found is allowed) for its email.
- **Phase 1, one transaction.** Read `users/{uid}` and `tickets` where `claimedByUid == uid`. Check the guards on that read, inside the transaction, so a concurrent invite acceptance (which reads the same document) aborts one side: 409 when `users.email` or the sign-in email is on `config/bootstrap.adminEmails` or `staffEmails` (a missing list is empty; compare lowercased); 409 when `speakerId` is set ("This account is linked to a speaker. Delete the speaker record first."). Then clear `claimedByUid` and `claimedAt` on each ticket, delete `users_public/{uid}`, `schedule_shares/{uid}`, and `users/{uid}`, and write the audit row `{ action: 'deleteAttendee', docPath: 'users/{uid}', uid, email, at }` (actor fields) in the same commit. Refuse with 409 naming the count when `4 + tickets` exceeds 500. After this commit the account is out of the directory.
- **Phase 2, the sweep.** Delete the sign-in (`auth.deleteUser`; `auth/user-not-found` counts as done). Remove bookmarks in transactions of at most 200: read each membership and its `sessionBookmarks` doc, delete the membership, and lower the count only when the membership existed (never below 0). Delete notes in batches of at most 400. List and delete files under `profile-photos/{uid}/` through `getBucket()`. Every step is idempotent.
- **Resume.** When `users/{uid}` is already gone, skip phase 1. Check the self and admin-email guards against the sign-in, if one remains. Write an audit row `{ action: 'deleteAttendee', docPath: 'users/{uid}', uid, email, at, resumed: true }`, awaited (500 on failure, nothing deleted). Then run phase 2 again. Return 404 only when no sign-in, bookmark, note, or photo file remains and no account exists.
- Response 200: `{ ok: true, uid, removed: { bookmarks, notes, tickets, photos } }`. If any phase 2 step fails, return 500 with code `delete-incomplete`: "The account is out of the directory. Some of its data could not be cleared. Try again." The retry takes the resume path.
- Approve and revoke are not edited.

## 4. Security and privacy

- **PII that leaves the deployment:** the export file. It has name, email, organization, role, registration status, badges, past attendance, social handles, and profile visibility, for every account on screen, private profiles included. It carries no uid, pronouns, bio, photo path, approval source, speaker id, or timestamps. It exists only in the response body and the admin's download.
- **What the rules enforce:** no client writes `users` except the owner, and the owner can write only the eleven self-editable keys, so `pastAttendance` is denied even to its owner, to set or to remove. No client deletes `users`, `users_public`, or `schedule_shares`. `admin_logs` is read-only to admins and closed to everyone else. A non-admin cannot read or list `users`.
- **A non-admin cannot** call any of the three endpoints (401 or 403), read the source rows, or set their own past attendance. They can read their own account document, which now includes `pastAttendance`.
- **A staff admin can** export, edit past attendance, and delete an attendee account. **A staff admin cannot** delete their own account, an operator or staff account, or a speaker-linked account. They cannot write the fields from the browser, change or remove an audit row, or get a file or delete a record without an audit row.
- **What a delete removes:** the account, the directory profile, and the schedule share, atomically; then the sign-in, saved sessions (counts corrected), private notes, the profile photo files, and the ticket claim. **What stays:** `admin_logs` rows, `sent_emails` rows, `feedback` rows that carry an address, the ticket record itself, and reaction markers (open question 1).
- **Residual risk:** an open session keeps a valid ID token for up to one hour after the sign-in is deleted. In that window it can still write its own `sessionNotes` or upload a photo, because both rules check only `request.auth.uid`. The report states this; a rules change is out of scope.
- **Abuse cases:** a formula in a name, organization, or handle label is escaped. A forged uid list reads `users/{uid}` only, and missing ids are skipped. An oversized list is a 400. A staff member who bulk-exports leaves a row with the count, the status filter, and whether a search narrowed it. That person can already read `users` in the browser, so the audit row is the control. Deleting an admin to lock someone out is refused. A deleted person who signs in again gets a new pending account with no history.

## 9. Decisions and open questions

Decisions the builder may not change without the director:

1. Organizer-owned fields are `pastAttendance` only. Reason: it is the one field in the approved export set with no source. Every other field belongs to the attendee (the rules allowlist) or to another server process (registration, speaker link).
2. "Role" is `jobTitle`, because the profile form labels it "Role". `users.role` is an access input and is never edited or exported.
3. "Contact details" means name and email. `users` holds no other contact field.
4. The client sends the uids on screen, and the server re-reads them. Reason: the file matches the screen by construction, with no second filter and no `packages/shared` change.
5. The file is returned in the response and never stored. Reason: `exports/` in Storage is world-readable.
6. The export audit row is required, and the file is refused without it. The delete audit row commits with phase 1, and a resumed delete writes its own row first. Reason: the "Done when" line, and a PII egress or an irreversible act must not go unrecorded.
7. The export audit row records the status filter and whether a search was used, never the search text. Reason: the text can name a person, and audit rows survive a delete.
8. All three endpoints are staff tier. Reason: staff runs attendees and already reads `users`. The admin-account guard stops staff from deleting operators.
9. A delete removes the directory entry atomically and sweeps the rest inline, retried by the admin, never by a queue. Reason: one transaction over every bookmark and note can pass Firestore's 500-write ceiling and strand an account that can never be deleted; the sweep has no ceiling, and each step is idempotent.
10. A speaker-linked account is refused, not unlinked, and the guard runs on the transaction's own read. Reason: seam #3.
11. No rules edit and no feature flag. The rules tests are the proof.
12. In-row editing, no new route. Reason: no new tier declaration and no docket change.
