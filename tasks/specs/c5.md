## 1. Issue and its "Done when" line

Issue #196, M10 item 7 (`docs/plans/2026-09-09-cjs-parity-gap.md:213`). The issue text is the contract:

> `cmsPublishQueue` is not a list of unpublished work: `cmsGetPublishQueue` returns operation rows created after `cmsPublish` starts, and `cmsUpdatePublishStatus` only marks one of those operations done or failed. Neither one knows about a saved draft. Add the missing half: a listing of dirty drafts, either a new admin endpoint or a derivation of each `_drafts` collection against its live collection, showing what is saved but not live, per collection. Wire the page's publish action to `cmsPublish`, and keep the existing operation rows as the progress and failure record beside it. The banner in the admin shell reads the same dirty draft source, not the operation rows. **Done when saving a block without publishing raises the count, publishing clears it, a failed publish operation is still visible as failed, and the banner and the page never disagree.**

Clauses to prove on the real surface: (a) a block save raises the count; (b) a publish clears it; (c) a failed run still reads Failed, however many runs follow it; (d) the banner, the page's figure, and the page's rows never disagree. Section 5 names the test for each.

Also binding: gap rows 102–103 ("The banner must read that source, never the publish operation rows, or the count means something else"); the M10 done line (plan 205: "the publish queue have pages"); design record §8 (#196 takes the count, legend and figure sentence, the notice bar, and the ruled table) and §3.4 (admin devices: the pending-changes banner, the queue row with a state word and one action, the figure sentence, the ruled table).

## 3. Design

### 3.1 Data model

No new collection, field, index, or queue. The page and the banner derive the listing in the browser from each `<C>_drafts` collection with the query `listDirty` runs. The state word comes from the draft alone: `basedOnRevision` is a number, so "Live with unpublished changes"; it is null, so "Draft". Every writer of a live doc is `publishDocs`, which sets `basedOnRevision`, so this matches `recordStateOf`. Writers stay `writeDraft` and `publishDocs`. Readers: admins of either tier, through the rules that exist.

### 3.2 Endpoints

**No new endpoint.** The page calls `cmsPublish` (staff on a4) in three forms: `{ all: true }`, `{ collection, docIds }`, and `{ queueId }`. `cmsPublish` already writes `admin_logs` (`cms-publish`, `cms-publish-failed`) and applies its limits: 2000 ids and the cmsSchedule parent rule. `cmsGetPublishQueue` and `cmsUpdatePublishStatus` are not changed.

### 3.3 Rules

No change. New rules tests pin the three list queries the browser now runs (section 5).

## 4. Security and privacy

- **Rules enforce (unchanged):** `<C>_drafts` and `cmsPublishQueue` are readable by operator and staff only, and no client writes them. `cmsPublish` checks the tier on the server.
- **Stored text:** c5 writes no stored text. On read, every draft name, id, email, run error, and note renders as a React text node. Nothing uses `dangerouslySetInnerHTML`, and no stored value becomes an `href`: editor links are built from ids, sections, and fields with `encodeURIComponent`. Names are cut at 80 characters (c4's rule). No rich text is rendered.
- **Non-admin:** the gate denies the route. A direct list query on any of the three shapes fails (rules tests). `cmsPublish` answers 401 or 403.
- **Staff:** sees the listing, publishes any collection (all six are staff content on a4), and resumes a failed run. Cannot read `admin_logs` (operator on a4). There is no control to mark a run done or failed.
- **PII:** admin emails (`updatedBy`, `requestedBy`) are shown to admins only. They are already readable by admins under the rules. Nothing leaves the deployment.
- **Abuse:** a hostile draft title renders as text (web test). Listeners read dirty drafts and queue rows only. A collection over 2,000 dirty drafts publishes through `{ all: true }`, which has no id cap.

## 9. Decisions and open questions

**Decisions the builder may not change without the director:**

1. **Derive in the browser, not a new endpoint.** A save must raise the banner at once on any admin screen. Listeners do that. An endpoint would need polling.
2. **The query is `where('status', '==', 'dirty')` on `<C>_drafts`, `listDirty`'s own.** The page, the banner, `{ all: true }`, b1, c1, and c2 then count the same set. The listeners read only dirty docs.
3. **One provider in the shell. The banner and the page only read it.** They share one value, so they cannot disagree. The provider holds counts and docs; grouping and formatting run in the lazy page.
4. **A new seam module with a default mock in `setup.js`,** not new listeners through `adminSource.js`. Otherwise the provider takes over the name-keyed mocks in two suites, or every suite needs a new mock export.
5. **The state word comes from `basedOnRevision`.** This needs no listener on the six live collections. `writeDraft` sets it (`store.test.cjs` 53, 70).
6. **Three publish actions, all `cmsPublish`:** Publish all (`{ all: true }`), per collection (explicit ids), and Resume (`{ queueId }`). A per-collection action lets pages go out while a session publish is refused. There is no per-row publish: each editor has one.
7. **Runs: the last 10 plus every failed run (up to 20), from live listeners, with one action on failed rows only.** A failed run must not scroll away while it is still failed (clause c). The sweep retires stranded runs, so there is no "Mark failed" control. `cmsGetPublishQueue` stays unused and unchanged.
8. **The banner is the admin's own pending-changes band (§3.4), not a3's `NoticeBar`.** It sits above the stone, shows only when the count is above 0 and off its own page, and puts no count on the rail. Deviations from the §3.2 Notice bar for the director to accept: no live role (a save is announced by the editor, and a second announcement would repeat it) and no dismiss (a dismissed count would hide unpublished work). Deviations from the §3.4 ruled table: no sort and no bulk-action row (the order that matters is newest first; the panel action is the bulk action).
9. **Docket: Content, last, "Unpublished changes", `/admin/unpublished`, tier staff, lazy.** The word matches the state vocabulary ("Live with unpublished changes") and b1's readiness column.
10. **No endpoint, rules, seed, flag, or public change.** Admin vocabulary only.

**Open questions, each with the default the builder takes:**

- Show the site snapshot (`publisher`) result on a run? Default: no.
- Offer a way to retire a failed run without resuming it? Default: no. It needs `cmsUpdatePublishStatus` in the UI; name it in the report.
- A per-row publish or checkbox bulk row? Default: no.
- Should Resume ask for confirmation, since it publishes the current draft of records edited since the run failed (`publishDocs` publishes any draft)? Default: no confirmation; the failed row states it. Name it in the report.
- If c4 is not on the tip, should c5 still ship c4's words and helpers? Default: yes, as stated in 3.4.
