## What changed

Commit "Send pitch receipts and staff-confirmed decision emails".

- Three new email templates: `pitch.receipt`, `pitch.accepted` and `pitch.declined`.
  They use the shared branded layout and text footer. Operators edit plain-text
  wording, not markup. `functions/src/email/templates/pitchNotice.cjs` builds both
  bodies from the wording: it HTML-escapes the wording, and render.cjs escapes each
  token value again. The shipped subject and wording live in
  `packages/shared/src/pitch.cjs`, so the admin editor can show and restore them.
- Automatic receipt. `submitSessionPitch` reads `session_pitch_settings/notices`
  and the demo policy inside the pitch transaction. In automatic mode it creates the
  pitch with `notices.receipt = { state: 'queued', attempt: 1, onceKey, ... }`. After
  the commit it sends through the central sender (`createEmailCore().send`) and
  records `sent` or `failed`. A replay finds the record and sends nothing. A failure
  never changes the 201 response. A historical demo queues nothing.
- `sendSessionPitchNotice` (staff). It previews (no writes) or sends a receipt or a
  decision email. It checks the expected status and revision, refuses an email that
  was already sent (`409 already-sent`), refuses a fresh queued one
  (`409 in-progress`, retryable after 10 minutes), refuses a receipt for an imported
  pitch, and refuses demos (`403 read-only-demo`, checked inside the transaction
  before any write). It writes the queued record and an `admin_logs` row in one
  transaction, then sends. A failed delivery returns `502 delivery-failed`. The
  decision is unchanged.
- `savePitchNoticeSettings` (operator). It saves the receipt mode
  (`automatic`/`manual`) and the subject and wording of each email. It validates
  every token with the existing `validateOverridePayload`, and it writes the
  settings with an `admin_logs` row. The shipped wording is stored as no override.
- Delivery records: `session_pitches/{id}.notices.{receipt|accepted|rejected}` with
  `state`, `attempt`, `onceKey` (`pitch-notice:{id}:{slot}:{attempt}`), `mode`, `to`,
  `feedback`, `reviewRevision`, `queuedAt`, `queuedBy`, `sentAt`, `error`.
- Rules: `session_pitch_settings/{docId}` is readable by both admin tiers. Clients
  cannot write it.
- Admin page: **Manage pitch emails** (operators) and **Emails to the submitter** on
  each pitch. The second shows each record as a word badge (Sending, Sent, Not sent)
  with the time, actor, attempt and failure reason. It has **Prepare the
  acceptance/decline email**: an optional note to the submitter, a preview (address,
  subject, text), a confirmation checkbox, and then Send. A changed note clears the
  preview. It also offers **Prepare a receipt** / **Retry the receipt** for native
  pitches.
- Docs: `docs/operator/session-pitches.md` (new "Pitch emails" section and API
  entries), `docs/ADMIN_GUIDE.md`, `functions/README.md`, `CHANGELOG.md`.
  `.github/smoke-endpoints.json` lists the two new endpoints. `docs/ROADMAP.md` has

## Decisions the owner may want to change

- The issue asks for "automatic and manual delivery modes". The dispatch said a
  decision email must never be sent automatically. So the mode setting applies to
  receipts only. Decision emails are always a staff action with a preview.
- Receipts default to **automatic** when no settings document exists. Existing
  deployments start to send receipts for new native pitches after deploy, with no
  opt-in step.
- Editable wording is stored in `session_pitch_settings/notices`, not in
  `email_templates`. That collection has no admin surface and no client read, and
  plain wording keeps html and text in step. The generic `email_templates/pitch.*`
  override path is not read for these emails.
- The decision email is keyed per pitch and per status. After an acceptance is
  sent, declining and then re-accepting never sends a second acceptance. The
  decline can still be sent once.
- A send that stops before it records a result stays `queued`. Staff can retry it
  after 10 minutes. If the first send did reach the provider, a retry can deliver a
  second copy. The UI shows a queued record as **Sending**.
- A failed decision send returns HTTP 502 (`delivery-failed`). The record and the
  decision are both kept.
- Receipts are sent inline after the commit, like the feedback confirmation. They
  add the provider's latency to the submit response. No queue was added.
- The note to the submitter is stored on the private pitch record and in
  `sent_emails`.
