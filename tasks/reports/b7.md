Key decisions in the record:

- Scope: `https://www.googleapis.com/auth/calendar.app.created`, and no other. It writes only to a calendar the app created. Google listed it as non-sensitive when written; the record tells the operator to confirm the classification in the console before configuring and says what changes if it is sensitive.
- The client's own Google Cloud project owns the consent screen and the OAuth client (the Firebase-created web client). The client verifies; the operator does the console work under the client's authorization. An operator-owned client was rejected for brand and cross-project reasons.
- No secret. The browser gets a short-lived access token through Firebase Auth. No refresh token, no new Tier A variable, no Secret Manager entry, no rules change. The only stored value is the calendar id in browser local storage.
- Flag `calendarSync` (already in `KNOWN_FEATURE_KEYS`), off by default, and it requires `icsExport`. With the flag on before setup is finished, Google refuses the grant and the control shows "not granted" with the `.ics` download; nothing is written.
- Sync model: one secondary calendar per attendee, one tagged event per bookmarked session in the event's time zone, reconcile-on-pass, passes only while the My schedule page is open, no queue, retry is the next pass.

Tests added: none. This is a documentation change. `scripts/build-pages.test.cjs` covers the manifest entry and the fragment links in the record.
