## Review findings and fixes

1. **BLOCKER, #248 not met for the reported case.** `sessionDoc.js` fixed
   the "day has no label" fallback but still fell through to the raw id
   (`dayLabel.get(dayId) ?? dayId`) when a session's `dayId` names no entry
   in `config/event.days` at all — exactly the review's repro:
   `e2e/fixtures/answers.json` configured only `day-1`, `seed-demo-event.cjs`
   seeds sessions on `day-1`/`day-2`/`day-3` but skips writing `config/event`
   because it already exists (`decideConfigWrite` skips an existing doc), so
   `day-2` and `day-3` sessions had no matching day record and their group
   heading fell back to the bare id. The same happens when an operator
   deletes a day sessions still reference.

   Fixed: `mergeSessionRevisions` now gives a group whose `dayId` matches no
   configured day the plain heading `"Not on a configured day"` (exported as
   `UNKNOWN_DAY_LABEL`), never the id, sorted after configured days and
   before "Unscheduled" (the existing tie-break sort already does this:
   an unmatched id gets `Number.MAX_SAFE_INTEGER` like `unscheduled` does,
   and alphabetically `d`/most real ids sort before `u`). I kept each
   orphaned `dayId` as its own group (not merged into one shared bucket)
   because merging would have broken the existing parent/child grouping
   logic inside `mergeSessionRevisions`, which compares a row's real
   `dayId` against the group's key — merging distinct ids under one
   synthetic key would make that comparison always mismatch for rows in
   that bucket.

   `AdminSessionEditor.jsx`'s "Event day" `<select>` had the matching
   problem: a saved `dayId` not among the rendered `<option>`s makes the
   browser show the first option ("Select a day") while the stored value is
   still the orphaned id — silently misleading. It now adds one synthetic
   option naming the actual stored value, e.g. `"day-9 (not on a configured
   day)"`, so the control's displayed state matches its real value and the
   id is still visible to the operator who has to fix it (this one case
   does show the raw id, deliberately — a select that has to name a value
   for an operator to correct is a different job from a list heading, and
   hiding the id there would leave them with nothing to act on).

   Fixed the actual root fixture, per the issue's original scope item: added
   labelled `day-2`/`day-3` entries to `e2e/fixtures/answers.json` (dates
   `2027-05-14`/`2027-05-15`, following `day-1`'s own date base — the ascending
   date order the schema requires), so `config/event.days` now covers every
   day the demo seed's sessions reference and the e2e suite no longer
   exercises the orphaned-day path by accident.

   Ran `npm run test:e2e` under the shared lock after this fix: **11/11
   passed** (full Firestore/Storage/Auth/Functions emulator suite + Playwright
   Chromium), confirming the fixture change didn't disturb any journey.

   Corrected: my first report claimed no current fixture reproduced the bug.
   That was wrong — the review's repro is real and reachable through the
   ordinary e2e bootstrap sequence (`init-event.cjs` from `answers.json`,
   then `seed-demo-event.cjs`), not just through hand-editing. The CHANGELOG
   line for #248 is corrected to describe both fallback cases.

   New tests: `sessionDoc.test.js` (`mergeSessionRevisions` with a session
   on an unconfigured `dayId`, matching the review's exact repro shape) and
   `AdminSessions.test.jsx` (the day select showing the orphaned value

## #227 — Treat a blank number field in the venue editor as an error, not zero

Bug fix, test-first.

Investigation: the marker x/y coordinates already went through a
`coordinate()` helper that correctly returns `null` for a blank field
(added for #159) — already correct, including its field-error behaviour via
`validateVenueMap`. The live bug was `venueReferencesPayload`'s
`walkingMinutes: Number(movement.walkingMinutes)`. The local validator
(`validateVenueReferences`) already flags a blank field with a message
while typing, and `AdminEventSettings`'s `submit()` already refuses to send
while either validator has errors (both pre-existing on this branch's
history) — but the payload function itself still silently coerced a blank
to `0` if called directly or if that gate were ever bypassed.

Changed:
- `apps/web/src/admin/components/VenueReferenceEditor.jsx`: new
  `wholeMinutes()` helper, the same shape as `coordinate()`. A blank or
  non-numeric walking-minutes value now resolves to `null`, never `0`.
- Tests: `VenueReferenceEditor.test.jsx` — new payload-level case for blank
  and whitespace-only walking-minutes values.

Keyboard path / visible focus: unchanged — `focusFirstError` already moves
focus to the first invalid field on submit.

**Done when**: met in full.
