## What changed

Server, `functions/src/cms/versions.cjs` (the only server file changed). `cmsGetVersionHistory`
keeps its request, its limits, its staff gate (a4) and its `{ entries, nextCursor }` shape. Each
entry is now built by `toEntry` from named fields only: `id, docPath, revision, fields, visible,
publishedAt, publishedBy, publishedByUid, previousRevision, changes, moreChanges`.

- `publishedAt` is milliseconds. A Firestore Timestamp has no `toJSON`, so before this change it
  left as `{ _seconds, _nanoseconds }`.
- `changes` comes from `describeChanges(previous, current)` (pure, in `internals`). The
  predecessor of each entry is the next row of the same query. The query already reads one row
  past the page for `nextCursor`, so the last entry on a full page has its predecessor too, with
  no extra read. Fields flatten to dotted paths: a map by key, an array of scalars as one value,
  any other array by index, an empty map or array as one value. An instant is one value in
  milliseconds, marked `time: true`. `seeded` and `seededAt` are never a change. `visible` shows
  when it moves, and on a first version that went out hidden. Paths sort segment by segment, an
  index by number. At most 50 changes; `moreChanges` counts the rest.
- `fields` is the stored snapshot with every instant as an ISO string, so the page can send it
  back to a save endpoint (the restore, below).
- No new endpoint, collection, index, rule, queue or `admin_logs` row. `functions/index.js` and
  `.github/smoke-endpoints.json` are unchanged.

## Departures from the spec, and why

1. **Restore is built.** Spec open question 1 said no. The dispatch message names "an E2E case that
   edits and publishes a record, opens its history, and restores an earlier version through the
   admin" as the real-surface proof, so I read that as the director's answer to the question. To
   keep the write surface where it is, the restore adds no endpoint: the page sends the version's
   fields through the record's own save endpoint (`cmsUpdateContent`, or `cmsCreateContent` for a
   deleted record, `cmsSavePage`, `cmsSaveUpdate`). Every check that save runs applies (speaker and
   parent references, the stat contract, page path uniqueness and the system page guards, the
   update shape), and c1's, c2's and c3's new checks will apply with no change here. That save
   writes its own `admin_logs` row (`cms-update-content` and the like); there is no separate
   restore row. The generic endpoint merges, so a field the current record holds and the version
   does not is sent as `DELETE_FIELD_SENTINEL`; the seed flags are never sent. Restoring writes the
   draft only; the publish is a second, explicit press. For this the `fields` snapshot now carries
   instants as ISO strings (the spec said "as stored"; `cmsSaveUpdate` accepts ISO).
2. **The record list uses b1's `RuledTable`** (`admin/components/RuledTable.jsx`, on the base
   since the spec was written) instead of a copy of `GalleyHead`'s classes. It draws the same
   sticky head, the focusable region named by its caption ("Records"), and `aria-sort`.
3. **Page tests mock `useAdminApi`**, not `fetch`: the convention the email log and attendee page
   tests follow, and the one the dispatch message names for the shell.
4. **`describeChanges` returns `{ changes, moreChanges }`**, so "no change" is
   `{ changes: [], moreChanges: 0 }`, and the cap lives in one place.
5. **The public check in E2E case 3 uses a fresh browser context.** The signed-in operator is sent
   to "Complete your profile" from the home page, so the old subtitle is read as a visitor.
6. Additions the spec did not ask for: "This is the published version." on the live version, and
   no restore offered on that version while no newer draft sits over it (a restore would change
   nothing).

## Decisions the owner may want to change

- Restore writes the draft; publishing it is a second press ("Publish now" or the editor). A
  one-press "restore and publish" would be one call more.
- A restore of a deleted record creates it again as a draft. Its route is the only way to reach
  it: the list shows records that exist now (spec decision 5).
- The shown account is the publisher, `init-event-script` for the seed, in mono as stored.
- Times read on the event clock with the zone named; the reader's clock when the event has none.
- A value published by mistake stays; removing it is a database console task (spec open question 7).
