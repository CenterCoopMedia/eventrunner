## #231: Social accounts in event settings, and legal and social schema validation

What changed:

- `packages/shared/src/config/schema.cjs`: `validateEventConfig` now validates `legal`
  and `social`. Legal: an object or null; unknown fields refused by name
  (`operatorName`, `postalAddressHtml`, `supportEmail`, `conductEmail`,
  `reviewRequired` are the only ones); the two text fields null or a string; the two
  addresses null, empty, or an email address; `reviewRequired` a boolean. Social: an
  object or null; unknown fields refused; `hashtag` null or one word with no spaces;
  `handles` an array of `{ platform, handle?, url }` with unknown fields refused,
  `platform` required, `platform` and `handle` at most 40 characters, `url` checked with
  `safeUrlHref` from `shared/urlSafety` (no second validator), and the same service plus
  canonical link refused twice. New exports: `LEGAL_KEYS`, `SOCIAL_KEYS`,
  `SOCIAL_HANDLE_KEYS`, `MAX_SOCIAL_LABEL_LENGTH` (shims updated in `schema.mjs` and
  `config/index.mjs`).
- Server: `functions/src/admin/config.cjs` already runs `validateEventConfig` on the
  merged document inside the write transaction, so the new rules apply to
  `updateEventConfig` with no code change. Its header comment is updated, and endpoint
  tests prove the refusal and that nothing is written.
- Email: every built-in template now lists the accounts in its footer (commit 5).
  `functions/src/email/templates/layout.cjs` adds a footer row with
  `{{social_links_html}}` to `wrap()`, and exports `TEXT_FOOTER`, which all eight
  templates' text bodies now end with: the postal block, then one "Service: link" line
  per account from a new plain token, `social_links_text` (`render.cjs`). That token also
  guards the html row, because `{{#if}}` reads plain values only. An empty list adds no
  row and no blank line. Both tokens are in `LAYOUT_TOKENS`. `render.cjs` filters the
  accounts through `safeUrlHref` and drops a blank service name, the same set the site
  footer shows. `send.cjs` is unchanged: it appends the legal block to non-template mail
  because the law needs it there, and nothing needs the accounts there.
- New `apps/web/src/admin/components/SocialHandlesEditor.jsx`: a Social accounts panel
  (service, optional handle, link per row; add and remove; the hashtag field moved here
  from Operator and search). It follows the venue editor's repeater: labelled fields,
  add in the panel head, a remove button per row, focus moved to a surviving control
  after a removal, and a status line. Add moves focus into the new row's service field.
  The hint examples are neutral (`#EventName`, `@eventname`).
- `apps/web/src/admin/pages/AdminEventSettings.jsx`: loads and sends `social.handles`;
  checks the rows at submit like the venue map (#219 pattern: the save stays enabled, the

- `scripts/lib/answers.cjs`: an optional init-event prompt, `event.social.handles`, as

## Venue editor fix found while reading for #226

In `apps/web/src/admin/components/VenueReferenceEditor.jsx`, all test first:

- Commit 2. A new place's id was filled from the name only while the id was empty, so
  typing "Main hall" key by key left the id as "m". Rows were keyed by the value being
  edited, so each change rebuilt the row and dropped keyboard focus. Rows are now keyed by
  position.
- Commit 6. The commit 2 version inferred "the id still follows the name" from equality
  with the name's slug, so an id typed by hand could be taken back. Each row now carries
  an `idTouched` flag, set by the id field and never sent. The name drives the id only
  while that flag is off and the place is unsaved. When an unsaved place's id changes,
  every movement end and map marker that named the old id is rewritten to the new one in
  the same change. I applied this to a hand-typed id change on an unsaved place too, not
  only to a following id, because it leaves the same dangling references. Nothing is
  rewritten from or to an empty id, or from an id another row shares.

Tests: 7 in `VenueReferenceEditor.test.jsx` (whole-name fill, hand-typed id stops the
fill, a typed id survives a name that later slugs to it, focus stays in place, movement,
and marker fields, references follow a new place's id, a saved id never moves, the
payload carries no form flags).

## Decisions the owner may want to change

- The editor edits the optional `handle` as well as service and link. ADR 0001 defines
  `{ platform, handle, url }` and the site footer prints it; leaving it out would have
  dropped stored handles on save. The email footer prints the service name only.
- Links allow `http://` as well as `https://` (`safeUrlHref`), as for every other
  operator-typed outbound link. The registration URL stays https only.
- The email addresses in `legal` accept `''` as well as null, because init seeds `''`
  for an unanswered address.
- The hashtag stays unrendered, in the Social accounts panel, with a hint that says so.
- The demo fixture gains no handles: demo links would point at `example.org`. The demo
  was regenerated anyway.
- The 40-character cap is declared in `schema.cjs`, not required from `speaker.cjs`, so
  the speaker module stays out of the public first paint. A test holds the two equal.
- A stored template override that replaces a body keeps its own footer and so gets no
  accounts unless its author adds the tokens.
- A deployment whose stored `legal` or `social` block already carries an unknown field
  will have every event settings save refused until that field is removed from the
  document; merge-then-validate means the admin cannot remove it. No seed or fixture has
  one.
- `docs/ROADMAP.md` lists #226 and #231 only as plain numbers in the M7 follow-up line,
  with no checkbox. I left the line alone; builder a1 edits the same line.
