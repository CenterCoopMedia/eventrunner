## Departures from the spec

1. **The proof tint sits on each cell, not on the `<tr>`.** Checked in Chromium through the E2E
   harness: `.admin-proof-row::before` on a `<tr>` is laid out as an extra cell, so every cell moved
   one column right under the heads. On the cells the tint draws as a continuous row. The layer also
   paints over bare text, so every cell's content is an element; the web test pins both (four cells,
   each `admin-proof-row`, none holding a bare text node).
2. **The banner's `mx-auto w-full max-w-admin-canvas` wrapper is inside the banner component**, so
   nothing at all renders when there is no banner. The placement is the spec's: first child of
   `<main>`, before the `admin-stone` div, never inside it (shell test and E2E). The band adds
   `lg:px-lg` so its text lines up with the stone's wide gutter. (Review round: the in-sentence link
   now takes `admin-target` as an inline-flex box, 24px tall on a pointer and 44px on touch.)
3. **The provider wrap in `AdminLayout.jsx`** is a five-line `AdminLayout` that renders
   `PendingChangesProvider` around the old body, renamed `AdminDesk`, so the shell's JSX is not
   re-indented and the diff stays additive.
4. **Focus after a publish waits for the answer.** When the pressed control leaves with its panel
   while the call runs, focus moves to the result line once the result is in it; the result line is
   `empty:hidden` until then. Web: "moves focus to the result once it arrives when the panel left
   before the answer".
5. Small copy the spec left open: the runs error reads "The publish runs could not be refreshed.
   The list will try again."; `summarizeAll` says "picks it up live" for one change and "picks them
   up live" for more.
6. **Bundle.** After the review round the admin entry chunk grows by 2,902 raw and 911 gzip bytes
   against the base, under the spec's 3,000 raw and 1,200 gzip. (Before the review round it grew by
   3,333 raw, over the raw cap.) No ceiling was raised.
7. **Two seams, not one** (review round). The publish run reads live in `publishRunsSource.js`,
   which only the lazy page imports, so they stay out of the admin entry chunk. They reuse
   `listenWithRetry` from `pendingChangesSource.js`.
8. **The banner finds its own page with the router's `matchPath`** (review round), which is already
   in the first-paint bundle: any case and a trailing slash match, as the route does. A
   percent-encoded spelling of the address (such as `/admin/%75npublished`) is not decoded, so on
   that hand-typed address the banner also shows on its own page, stating the same count. Decoding
   it with `useMatch` would add 98 raw bytes to the first-paint chunk, which every visitor loads.

c4 and c3 are not on this base, so, as the spec says: `COLLECTION_CHOICES` lives in
`collectionWords.js` with the label "Timeline" (review round: the Overview's word), and
`recordNameOf`, `formatPublishedAt` and `toMillis` live in `pendingChanges.js` under c4's names and
rules. c4 imports them from there (or re-exports `COLLECTION_CHOICES`).

## Decisions the owner may want to change

- No control retires a failed run without resuming it; `cmsUpdatePublishStatus` stays unused. The
  maintenance sweep (every 30 minutes) marks a run with no progress for 90 minutes failed.
- **Resume publish** asks for no confirmation. The failed row says it publishes the current saved
  version of each record the run did not reach, which can include edits made after the failure.
- No per-row publish, no checkbox bulk row, and no sort: the order is newest save first, and the
  panel's button is the bulk action.
- The failed-runs read lists the 20 newest runs still marked failed (review round: ordered by
  `requestedAt` descending, with its composite index). Past 20 failed runs, older failed runs are
  not listed until newer ones are resumed. A failed row with no `requestedAt` is not listed;
  `cmsPublish` always writes one.
- Speaker pending edits are not counted; the empty state says they are reviewed on each speaker's
  page.
- The run rows do not show the site snapshot (publisher) result.
- The banner has no live role and no dismiss control, and the rail shows no count (spec decision 8;
  it is the admin's own band, not a3's `NoticeBar`).
- The Overview's readiness panel is a read-time snapshot, so it can lag the live banner until
  **Refresh figures**.
- `apps/web/src/components/NoticeBar.jsx` still names issues 196 and 199 as its consumers in a
  comment. #196 does not use it; the comment is left for d1 (#199), which edits that file.
