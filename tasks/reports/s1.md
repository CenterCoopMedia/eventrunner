## Findings

### js/polynomial-redos: real

- `packages/shared/src/config/schema.cjs:586, :592, :683` and
  `packages/shared/src/speaker.cjs:315`: the email pattern
  `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` is quadratic on a value that fails. A
  50,000-character dot-heavy value took about 1.9 s (8.7 s for the 4 config
  fields). The same pattern was copied into 7 more files that CodeQL did not
  flag. The worst one is `functions/src/auth/otp.cjs`: the OTP send and verify
  endpoints accept the value from anyone, with no length cap.
  - Change: new `packages/shared/src/email.cjs` (with `email.mjs` shim and a
    `shared/email` export) holds `EMAIL_ADDRESS_RE =
    /^[^\s@]+@[^\s@][^\s@.]*\.[^\s@]+$/` and `isEmailAddress`. All 9 copies
    use it (schema, speaker, otp, access, csvImport, commerceAdmin,
    SignInPanel, AdminAccess, Tickets).
  - Tests: `packages/shared/src/email.test.cjs` (old and new patterns agree
    on every string up to 7 characters over `a . @ space`; 4 hostile values
    each under 50 ms), `schema.test.cjs` "refuses a long hostile address in
    linear time", `speaker.test.cjs` "a long hostile email is refused in
    linear time", `functions/src/auth/otp.test.cjs` "the OTP endpoints refuse
    a long hostile email in linear time" (real handlers, 400 in under 50 ms;
    1.9 s before).
- `packages/shared/src/richText.cjs:87`: `/<hr(?:\s[^>]*)?>/i` is quadratic
  on repeated `<hr\t` (820 ms on 50,000 characters). Input is CMS rich text
  from an editor, checked in the browser and again in
  `functions/src/cms/blockTypes.cjs`. Worst case: a staff editor stalls a
  function call. Change: find the first `<hr` with a space or `>`, then look
  for a later `>`; tag removal is an indexOf scan. Tests:
  `richText.test.cjs` "treats tags, dividers, and stray brackets as before"
  and "decided in linear time on hostile markup". A one-off check of every
  value up to 6 characters over `< > h r b space / x` agreed with the old
  code. That check is not committed, because it has to hold the old
  patterns, which CodeQL would flag again.

### js/incomplete-multi-character-sanitization and js/double-escaping

- `functions/src/email/render.cjs:58` (both rules). Double escaping is a real
  bug: `&amp;` was decoded first, so `&amp;lt;` in a postal address reached
  the text body as `<` instead of `&lt;`. The tag finding is not an
  injection: the input is admin-written config HTML, the output is the
  text/plain body, and one `/<[^>]+>/` pass already left no closed tag. The
  pattern was quadratic on unclosed `<` (2.6 s on 50,000). Change: decode the
  5 entities in one pass; remove tags with one linear scan with the same
  result. Tests in `render.test.cjs`: "an _html token decodes each entity
  once in the text body", "leaves no tag in the text body, however it is
  nested" (both through `render()` and the real postal token), and
  "stripHtmlToText is linear on unclosed and nested brackets".
- `packages/shared/src/richText.cjs:88`: not an injection. The stripped text
  is only measured, never rendered. It is fixed as part of the linear rewrite
  above.
- `scripts/lib/markdown-pages.cjs:657, :695`: not an injection. The input is
  repository Markdown, and the renderer escapes every `<`. Two real but minor
  bugs: (1) the description decoded `&amp;` first, so a paragraph that shows
  `&lt;b&gt;` got `<b>` in its meta description; (2) comments were removed
  once, so `<!<!-- -->-- note -->` showed `<!-- note -->` on the page as
  text. Change: one-pass `unescapeHtml`; comments and description tags are
  removed until none is left. Tests in `scripts/build-pages.test.cjs`: "an
  html comment rebuilt by removing an inner one never reaches the page" and
  "the description reads the first paragraph as the page shows it". No
  committed page changes because of this (build-pages --check differs only
  in the changelog page).

### js/bad-tag-filter: lint script

- `scripts/check-copy-style.cjs:231`: `</script >`, `</SCRIPT\t>`, and an
  end tag with a newline were not matched, so the body was read as prose.
  This is a false-finding bug in a dev lint, not a security issue. The end
  tags are now `<\/script\b[^>]*>` and `<\/style\b[^>]*>`. Test:
  `check-copy-style.test.cjs` "html script and style bodies are not prose,
  whatever their end tag spells" (fails on the old code).

### js/incomplete-hostname-regexp and js/incomplete-sanitization in the demo bundle: third party

`docs/demo/assets/Profile-*.js:16, :47` is `@firebase/storage`
(`Location.makeFromUrl`): `DEFAULT_HOST = 'firebasestorage.googleapis.com'`,
`host.replace(/[.]/g, '\\.')`, and
`'(?:storage.googleapis.com|storage.cloud.google.com)'`. The same lines are
in `node_modules/@firebase/storage/dist/index.esm.js:27, :318, :323`
(0.14.4, from firebase 12.17.1). The latest `@firebase/storage` (0.14.6,
checked with `npm pack`) still has them, so an upgrade does not clear them.
They are not exploitable here: the host is the SDK's own constant or our
configured bucket or emulator host, never user input. Our source has no
such pattern.

Options, least bad first:
1. Dismiss the 4 alerts in the GitHub UI as "used in tests / not
   applicable" with this evidence. This is a triage decision for the
   owner. They come back with new hashed file names after each demo rebuild.
2. Stop committing `docs/demo` and deploy Pages from a workflow artifact.
   Code scanning then never sees the bundle. This is a larger change to the
   Pages flow.
3. Switch to advanced setup with `paths-ignore: [docs/demo]` in a CodeQL
   config. Default setup cannot take a config file.

Uncertain: whether `linguist-generated=true` in `.gitattributes` makes code
scanning default setup skip or hide `docs/demo`. I could not reach
docs.github.com from this sandbox to check, and I do not know it for
certain. I did not add the attribute. It is cheap to try. If it does not
work, it does no harm beyond collapsing the bundle in diffs.
