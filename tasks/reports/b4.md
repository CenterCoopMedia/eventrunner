## What changed

**Server.** `functions/src/admin/changeRequests.cjs` (new), in `functions/index.js` and
`.github/smoke-endpoints.json`:

- `submitChangeRequest { message, page?, submissionKey? }`. The order: 405; the flag, read live from
  `config/features` (off, missing, or not exactly `true`: 404, nothing written; a failed read: 500);
  401 with no token; 403 without a verified email; 413 over 8 KiB; 400 for the message (1 to 2000
  characters after trim), the page (text, at most 200, blank is null), or a malformed key. Then one
  transaction reads the request and `change_request_rate_limits/{uid}`. A stored request of the same
  account is a replay: 201, nothing written. More than 5 in 15 minutes: 429 with `Retry-After` and
  `retryAfterSeconds`, nothing written. Otherwise it writes the slot, creates the request (`status:
  'new'`, `uid` and lowercased `email` from the token, `createdAt`, `updatedAt: null`, `updatedBy:
  null`), and sets the `admin_logs` row, together. 201 `{ id, ok: true }`.
- `updateChangeRequestStatus { id, status }` and `deleteChangeRequest { id }`: staff tier
  (`requireAdmin(..., { tier: 'staff' })`), not flag gated. Each commits its write and its
  `admin_logs` row in one transaction; 404 for an unknown id writes nothing.
- The audit row is exactly `{ action, docPath, uid, email, at }`, the fields `logAdminAction`
  writes. It never holds the message. `store.cjs` is not edited.

**Rules.** `change_requests`: read `isAdmin()` (either tier), write `false`.

## Departures from the spec

1. **The rate limit is inside the submit transaction.** The spec had a separate
   `takeChangeRequestRateLimitSlot` transaction before the store transaction. Then a failed commit
   leaves a spent slot, which breaks the spec's own atomicity test ("leaves the store as it was"),
   and every retry of a stored request spends a slot. One transaction now reads the request and the
   window and writes the slot, the request, and the row together.
2. **The flag is read live from `config/features`**, not through `getConfig()`. `getConfig` is the
   five-minute container cache (`core/config.cjs`), so a flag turned off would still admit
   submissions for up to five minutes. A failed read refuses (500). The E2E proves the next request
   after turning the flag off is refused.
3. **A `submissionKey` another account already holds is 409 `conflict`**, nothing written. The spec
   answered 201 for any existing document, which would tell the second sender "We got your request"
   when nothing was stored.
4. **The server test uses the shared `cms/firestoreFake.cjs`.** It already buffers transaction
   writes, has a transactional `create`, and has the `beforeCommit` hook that fails a commit.
5. **E2E added** (the spec said none), as the director asked.
6. Smaller: the dialog's success heading is "Request sent" and focus moves to Close (the send
   control is gone); the message field has a privacy hint ("Only the event team reads your request.
   It is stored with your sign-in address."); status and delete bodies refuse a bad id as
   `id: must be a change request id.`
