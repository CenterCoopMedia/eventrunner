## #356 Eventbrite webhooks require unprovisioned HMAC

What changed:

- `eventbrite.cjs`: no HMAC check. `registerWebhook` registers
  `<callbackUrl>?token=<TICKETING_WEBHOOK_SECRET>` (https only).
  `verifyWebhook(rawBody, headers, { query })` compares `query.token` with the
  secret through `safeEqual` (SHA-256 digests and `timingSafeEqual`). A
  missing, empty, repeated, or wrong value gives `invalid_secret` before the
  body is read.
- Secret length: at least 32 characters, checked where the secret is used, not
  at construction. Every ticketing function builds this provider, so a short or
  missing secret only refuses every delivery and makes `registerWebhook` throw.
  Claim, verify, sync, and status keep working. No error prints the secret.
- `api_url`: https on `www.eventbriteapi.com`, with no port or credentials, in
  one of three shapes. `/v3/events/{e}/orders/{o}/` is the shape the first
  fixtures assumed. `/v3/orders/{o}/` is the documented shape for `order.*`; the
  event check then happens when sync re-fetches the order, and `sync.cjs`
  already drops an order for another event (now tested). For the documented
  `attendee.*` shape `/v3/events/{e}/attendees/{a}/`, the attendee is read from
  `API_BASE` to get its `order_id`. A 404 there, or no `order_id`, throws, so
  the handler answers 500 and Eventbrite retries. An authenticated delivery
  with bad JSON, an action the adapter does not handle (checked before any
  API read), or any other shape or host is valid with no order. The handler answers 200 + `not_actionable`, so
  Eventbrite does not retry. Nothing fetches the delivered URL.
- API error messages hide the secret (raw and URL-encoded).
- `functions/src/ticketing/webhook.cjs`: passes `{ query: req.query || {} }` as
  the third argument to `verifyWebhook`. Stripe ignores it; Stripe behaviour is
  unchanged. Still one queue, `ticket_sync_queue`.
- Fixtures: every delivery body's `config.endpoint_url` holds
  `?token=fixture-placeholder`. New `webhook-order-placed-order-path.json`,
  `webhook-attendee-updated-attendee-path.json`, `attendee.json`.
- Docs: `functions/README.md` ("Eventbrite webhooks"),
  `docs/EVENTBRITE_VERIFICATION.md` (section 1 is the sandbox check; the
  general sanitize rule now says to replace the token in
  `config.endpoint_url`; section 3 lists the three shapes to confirm),
  `docs/CLIENT_ONBOARDING.md`, `docs/DEPLOY_RUNBOOK.md`, `.env.example`,
  `scripts/lib/checklist.cjs`, `CHANGELOG.md`, fixtures README, the provider
  `index.cjs` comment.

## Codex review fixes (PR #494)

1. Redaction: it now also replaces the `URLSearchParams` form the registered
   URL uses (`~` and `!` encoded, space as `+`) and the `encodeURI` form. Then
   it blanks the token in any URL left in the message. Test: "a secret with ~,
   ! and a space never leaks through an echoed endpoint URL (Codex 1)".
2. Event scope on reuse: the stored `event_id` must equal the deployment's.
   An org-wide subscription is reused only by an unscoped deployment, and is
   otherwise stale. Tests: "an org-wide subscription (no event_id) is stale
   when the deployment is scoped to an event" and "an unscoped deployment
   reuses only an unscoped subscription".
3. Endpoint match: `endpointKey` is origin, path, and every query parameter
   except `token`, sorted. The token is still compared with `safeEqual`. Tests:
   "a changed non-secret query parameter is a different endpoint, not a reuse",
   "internals.endpointKey ignores the token and param order…". The earlier
   normalization test now covers host case, parameter order and encoding; an
   extra parameter no longer counts as the same endpoint.
4. An unhandled action is ignored before any API read. Test: "an unhandled
   action is ignored before any attendee read".
5. An attendee read that 404s, or has no `order_id`, throws, so the handler
   answers 500 and Eventbrite retries. Tests: "an attendee not readable yet
   (404 or no order_id) throws, so Eventbrite retries" and, on the real
   handler, "an attendee delivery whose attendee is not readable yet answers
   500 and writes nothing". `docs/EVENTBRITE_VERIFICATION.md` section 3 says
   so, and asks the sandbox to record how soon the read succeeds and how long
   Eventbrite retries a 500.

## Decisions the owner may want to change

1. Query parameter (`?token=`), not Basic auth in the URL userinfo as Postmark
   uses. A query string works with any sender that POSTs to the exact URL;
   userinfo depends on Eventbrite turning it into an `Authorization` header,
   which is unknown. Cost: Cloud Run request logs record the query string, so
   anyone with project request-log access can read the secret. Our code never
   logs it. Documented in `functions/README.md` and the verification runbook,
   with rotation steps.
2. Minimum secret length of 32 characters, checked when the secret is used.
   Before this change no real delivery could pass anyway.
3. The HMAC path is removed, not kept as an alternative.
4. An attendee delivery costs one API read in the webhook path, to find its
   order. A failure there, or an attendee the API cannot return yet, is a 500,
   which Eventbrite retries. An attendee that is gone for good is retried until
   Eventbrite stops.
5. An authenticated delivery the adapter cannot read is dropped with 200, not
   retried. If Eventbrite sends a shape we do not know, updates are lost
   silently until #79 records it. The alternative, a 401, gets retried for days.
6. Stale subscriptions are reported, not deleted.
7. `registerWebhook` ignores a narrower `events` list instead of throwing.
8. `docs/ROADMAP.md` has no line for #356 or #357, so nothing was ticked.
9. Operators must run `register-ticketing-webhook.cjs` again after deploy, and
   delete the old webhooks it names. The CHANGELOG entry says so.
