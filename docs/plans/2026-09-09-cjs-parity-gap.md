# CJS parity gap analysis

**Date:** 2026-09-09
**Target:** `/home/user/eventrunner` (Eventrunner, white-label event CMS, deploy per client)
**Reference:** `/home/user/cjs2026` (the live Collaborative Journalism Summit 2026 site, read only)
**Rule applied:** any feature an attendee, a speaker, or an admin can see or use in a browser on CJS is a parity gap if Eventrunner lacks it. Backend integrations with no browser surface are not gaps.

## Summary

Eventrunner covers the core of CJS and misses most of the surface around it. Sign-in, schedule, sessions, speakers, sponsors, updates, attendee profiles, materials, media, ticketing, and the block CMS all work. Of the 91 surfaces compared, 61 are missing and 20 are partial.

The largest gaps are: the site navigation ignores CMS pages, so seeded pages such as travel and FAQ are unreachable; there is no attendee dashboard and no speaker dashboard; the schedule has no search, filters, or sort; there is no admin overview with metrics; three CMS editors have working endpoints but no route; and there is no page metadata, sitemap, or social preview. Four surfaces need backend work before their screen can exist: the email log has no reader, the pending changes panel has no listing of unpublished drafts, an announcement to an audience has no batch send, and a shared schedule has no projection it can safely live in.

Eventrunner is already better than CJS in several places. The theme system has six presets, thirteen color roles, and a derived dark mode against one hardcoded palette. The admin has its own fixed identity and a grouped sidebar instead of a flat tab row. Pages are data, not code. Speakers have one canonical record instead of a three way sync. Materials use two collections instead of four. The schedule has a track grid, a print handout, and a back issue state. Feature flags, demo mode, credential free CI, an end to end suite, and the browser tool surface have no CJS equivalent.

## Proposed milestones

Six milestones and 70 issues, numbered from M7 because M6 exists. They run in dependency order and in order of visible impact: the public site first, then the attendee experience, then the admin and the CMS, then communication, social, and billing, then the speaker surfaces, which need the materials and profile work under them first. Every issue is sized so one agent can finish it with tests in one sitting. Three new area labels are proposed and used below: `area:attendee`, `area:admin`, and `area:social`.

### M7: Public site completeness

**Goal:** a visitor can reach and read every page the seed creates, and the site presents itself correctly to search engines and social previews.

**Done when:** every visible page doc appears in the navigation and the footer, each page carries its own metadata, and a fresh deployment serves a sitemap, a robots file, and a manifest.

1. **Render the navigation from page documents**. Tabs follow the keyboard pattern the interface guidelines set. Done when a speaker with two sessions can move between them and read both tabs by keyboard. Labels: `type:feature`, `area:speakers`.

Let a speaker send discussion points or session notes to the organizers from the session hub, stored on the speaker's own record through a server endpoint and mailed to `config/event.legal.supportEmail` through the existing provider, as one tokenized template beside the other speaker templates. Done when a submission is stored, the organizer receives it, a resubmission replaces the stored text rather than adding a second row, and a missing support address still stores. ## Risks and constraints

**Moderation surfaces.** The social feed, the post composer, custom badges, and the public change request form all accept text from people the operator does not control. None of them ships without a report path, an audit trail, and a way for an admin to remove an entry. Each is behind a feature flag that is off by default, so a client opts in and staffs it.

**PII projections.** `users` holds contact details and access needs; `users_public` is the only thing a browser may read. Shared schedules, attendee export, and invoice bill to details all widen what leaves the deployment. Every one of them needs a rules change, a rules test, and, for the export, the owner approved field set from the decision table.

**Firestore rules.** Rules are the enforcement, not the interface. Every new store in this plan needs its own rule and a test in `tests/firestore.rules.test.js` before the surface that reads it merges. Owner only subtrees, admin only reads, and server owned fields all follow the patterns already in `firestore.rules`. Three rows in this plan fail if that is treated as a rendering concern: an audience on `live_updates`, which is publicly readable today; saved sessions on `users_public`, whose read is authorized for the whole document from `profileVisibility`; and the email log, whose collection is closed to every client and stays that way behind a server endpoint.

**One queue.** `ticket_sync_queue` is the only queue in the system, per `CONTRIBUTING.md`. Scheduled broadcasts, retry collections, and pending work documents are out. The announcement composer sends inline and lets the mail provider own retry and pacing. Anything that cannot work that way needs an architecture decision record first.

**Hex literal ban.** Colors come from theme tokens. The lint sweep rejects hex literals everywhere except the mail templates, the schedule PDF, and the generated stylesheet. The invoice document generator sits with the schedule PDF; every browser surface in this plan uses tokens.

**Public repository hygiene.** This repository is public. No CJS names, cities, venues, palettes, or domains enter the code, the tests, the fixtures, or the seed. The seeded recap, guidelines, and city guide pages ship as empty sections with descriptions, never as another event's copy.

**Accessibility bar.** `docs/interface-guidelines.md` is what reviews apply. Filters, tabs, the tour, the composer, the crop control, and the mobile filter panel are the risky ones: each needs a keyboard path, visible focus, and a state marked by more than color. Reveal on scroll, ambient animation, pulse dots, and glass panels are rejected patterns, so several CJS treatments are deliberately not reproduced.

**Dependencies between milestones.** M7's navigation issue unblocks the travel, FAQ, recap, guidelines, city guide, and resource card rows, and its visibility and feature gate rule is reused by the footer and the sitemap. M8's filter issues must land before the URL state issue; its photo field issue serves the speaker headshot in M12; its schedule projection issue blocks the shared schedule page; and its calendar sync decision record is reviewed and accepted before any calendar code. M9's statistics endpoint blocks the overview and both panels, the admin tier issue blocks the access page, and the email log needs its server endpoint before its screen. M10's organizations editor blocks the sponsor detail page and the invoice form in M11, and its dirty draft listing blocks the pending changes banner. In M11 the provider batch send lands before the composer, and the social issues land in order: store and moderation first, then the composer, then the inbox. M12 comes last because the speaker dashboard reads the profile, materials, and live update work that M8 and M9 finish, and because its countdown reuses the M7 one.
